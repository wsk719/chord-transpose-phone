# 系統互動、文件儲存、環境清理與版本控制全域規範

## 執行指引
當使用者提出任何需求、修改建議或專案任務時，系統必須嚴格遵守以下複合流程，全程嚴格控管 Token 消耗、維持專案目錄純淨，並確保每一次變更皆有版本追蹤：

### 第一階段：先理解，不盲動（極簡對話）
1. **絕對不要先進行程式碼或檔案的實質修改**。
2. 遇到需求時，請先完全理解。若有不懂或模糊之處，必須先向使用者發問釐清。
3. **拒絕客套與廢話**：對話時跳過所有問候語（如：「好的，我了解了」）。直接輸出核心提問、計畫或成果。

### 第二階段：全域本地化儲存與需求歸納（預設原則）
1. **全域本地化儲存規範（最高原則）**：所有與專案相關的 `.md` 檔案、規範原則、架構說明、技術文件或指引資料，預設一律必須實質儲存於目前專案目錄之下（以相對路徑 `./` 或 `./.agents/` 為準）。嚴禁將任何專案特有的規格文件儲存到專案目錄以外的系統暫存夾或外部路徑。
2. **自動歸納整合對話需求**：系統在理解需求的同時，必須主動將對話中所有散落、多面向的使用者原始需求，自動進行歸納與結構化整合。
3. **指定的計畫檔相對路徑**：歸納後的需求與規劃解法，必須實質寫入並更新至 `./implementation_plan.md`。
4. 將歸納好的需求與計畫呈現給使用者，經過使用者明確確認同意後，才能進行實際的程式碼修改。

### 第三階段：極簡實作、環境清理、知識沉澱、版本控制與交付（專案瘦身與追蹤）
1. **僅輸出變更片段 (Diffs Only)**：在實作修改時，除非使用者明確要求，否則嚴禁重寫或輸出整份檔案。只顯示修改涉及的上下數行或目標函式。
2. **環境清理與無關檔案刪除**：在任務實作完成、驗證通過後，**系統必須立即主動檢查並徹底刪除所有在開發過程中產生的臨時測試腳本、實驗性程式或偵錯日誌檔（如 `temp.py`、`check.txt`）**。
3. **專案知識與學習沉澱（新增最高原則）**：在任務實作完成且環境清理後，AI 必須主動回顧本次對話中「學到的專案新知識、新架構、特殊業務邏輯、第三方套件踩坑紀錄或最佳實踐」。系統必須將這些新知識，以「條列式、帶有日期標記」的形式，實質追加（Append）或更新至專案根目錄下的 `./project_knowledge.md`。確保該檔案成為該專案持續成長的實質知識庫。
4. **規則同步與儲存**：所有系統修改、新定義或修正，都必須同步更新至專案根目錄下的 `./System_Architecture_and_Rules.md` 以及 `./.agents/AGENTS.md`。
5. **自動化版本控制與提交**：確認垃圾檔案清理完畢，且 `./project_knowledge.md` 與規則檔案皆更新完成、正式單元測試通過後，系統必須**主動呼叫 Git 工具將所有變更加入暫存區（git add），並自動生成結構化的 Git 提交訊息（git commit）**。提交訊息格式必須嚴格遵循以下規範：
   `type(scope): description`
   （範例：`feat(workflow): 自動歸納對話需求、寫入專案知識並整合 git 自動提交功能`）
6. **主動提示記憶重置（Session Reset）**：當上述版本提交完成且變更安全儲存後，AI 必須在對話最後主動提示使用者開新對話（New Chat），以清空記憶包袱，節省 Prompt Token。

## Gotchas（踩過的坑）
- **垃圾檔案污染 Git 紀錄**：**嚴禁在執行「環境清理」前進行 git commit**！必須確保臨時檔案（如 `temp.py`）已經被徹底刪除，才可以呼叫 Git 提交工具，否則會把垃圾檔案永久鎖進版本歷史中。
- **遺漏知識沉澱**：執行 git commit 前，務必確認 `./project_knowledge.md` 已經實質寫入本次對話所獲取的專案結晶，切勿直接提交。
- **誤刪正式測試套件**：執行環境清理時，必須分清「臨時測試檔案」與「專案內既有的正式單元測試（如 `tests/` 目錄）」的分別。正式單元測試不可刪除。
- **未授權即改扣**：未收到「確認」或「同意」前，絕對不呼叫任何寫入檔案或 Git 提交的工具（Tools）。
